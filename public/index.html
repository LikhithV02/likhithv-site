DeltaVec

A search index for AI has to be rebuilt whenever the source documents change. DeltaVec rebuilds only the parts that actually changed, and never loses track of what was deleted.

problem

A vector store is a derived dataset. Tutorials embed a static corpus once; production sources mutate constantly. Inserts are trivial. Updates and deletes are where naive pipelines silently break, serving answers from text that no longer exists.

approach

Watermark change detection over a mutating Postgres source, SHA-256 content-hash diffing per chunk, and deterministic chunk IDs (uuid5(ns, "doc:index")) that make every load idempotent. Orphan deletion, tombstones for soft deletes, and a reconciliation sweep for hard deletes. Orchestrated with Dagster behind blocking quality gates; served over FastAPI in Docker.

result

A re-run with no source changes processes nothing and duplicates nothing. Editing one paragraph re-processes one chunk, not the corpus. Six demo scenarios each prove one failure mode is handled, pinned by integration tests against real Postgres and real Qdrant.

decisions I'll defend in an interview · 4 passed
✓ qdrant_not_faiss
Every operation here is a mutation. FAISS is a library tuned for a static index; upsert and filtered delete are first-class in a store, and caller-supplied point IDs are what make the load idempotent.
✓ vectors_and_bookkeeping_split
Qdrant owns vectors, Postgres owns the chunk registry, so change detection is an indexed lookup and reconciliation is a SQL join. Qdrant first, registry second: never record work as done before it is done.
✓ chunk_size_is_schema
Boundaries must be deterministic or every hash changes and the pipeline degrades into a full re-embed that still looks healthy. Chunk size and overlap are versioned, not tuned.
✓ checks_never_repair
Quality gates detect; a separate sweep repairs. A check that quietly fixes what it finds can never tell you your pipeline is broken.

[02]retrieveon-device document intelligence · shipped 2026

Anvit

An app that answers questions about your own PDFs (a contract, a report, a medical letter) without uploading them anywhere. The model runs on the phone itself.

problem

Document Q&A normally means sending the document to somebody else's server. For contracts, medical records and financial statements, that is exactly why people don't use it.

approach

A Kotlin Multiplatform app for Android and iOS running Gemma 4 locally through LiteRT-LM. Custom PDF and DOCX parsing with hierarchical chunking along sections, tables and lists, so each piece is a complete unit of content. On top, an agentic retrieval loop: query routing and decomposition, corrective relevance checks, native tool calling and self-critique.

result

Published on Google Play with collections, chat sessions, streaming responses, citations pointing back to the exact passage, and settings-driven model configuration.

constraints that shaped it
01A phone-sized model has no headroom for sloppy retrieval, so the quality of the document splitting does work a bigger model would otherwise absorb.
02There is no server to wait on, so the delay is the phone's own. Every extra reasoning pass has to earn itself.
03Citations are non-negotiable: privacy is the pitch, and an answer about your own contract that you can't verify is worthless.

problem

An agent that can approve refunds is an agent that can be talked into approving refunds. Money movement cannot depend on a model holding the line under pressure.

approach

A LangGraph ReAct agent with refund tools. To grant a refund it must call issue_refund, and that tool re-runs the deterministic policy engine before writing anything. Identity comes from a signed JWT, never from the chat. Around it: fuzzy injection flagging, an output sanitizer for unbacked “approved” claims, turn and token budgets, and row locks against double refunds.

result

Every policy branch is covered by unit, tool and live tests. A manipulative message can change the wording of a reply without changing what gets paid out, and that held under a simulated 2,500-user spike.
